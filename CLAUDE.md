# CLAUDE.md

Instructions for Claude Code (or any agent) working in this repository. See `docs/STATUS.md` for the current, dated build log — this file is for durable conventions that don't change session to session.

## What this is

"Personal OS" — an AI-native personal wellbeing/sustainable-performance app. Built from `master_prompt.md` (123-section spec at the repo root — read it before assuming a feature doesn't exist or deciding one is out of scope). Not a therapist, chatbot, mood tracker, or journaling app — see `master_prompt.md` §2 for what to explicitly avoid.

Current build status, what's verified working vs. genuinely not built, is tracked in `docs/STATUS.md`. Read it first before claiming something is or isn't done — don't re-derive from scratch.

## Non-negotiable principles (violating these is a regression, not a style choice)

- **Never fabricate data, patterns, or evidence.** If a dimension has no real tracked source (e.g. Focus, Stress), the UI shows an honest "None yet" — never a plausible-looking invented number. This shows up throughout: Brain tab dimension tiles, Today rings, Personal Operating Manual, Relationship map.
- **Rules before AI.** Every AI-generating code path is gated behind deterministic checks first (sample-size minimums, real statistical thresholds) — an LLM is never asked to produce an insight from insufficient or absent evidence. See `functions/generate-insight/src/*.js` for the pattern: gate → build grounded evidence → call AI only then.
- **AI is grounded, never free-form.** `functions/generate-insight/src/grounding.js`'s `buildGroundingPreamble()` constrains every AI call to the evidence handed to it, with hedged language ("appears associated with," never causal claims).
- **No streaks, no gamification, no guilt.** No streak counters, no mascot/chatbot avatar — personality comes from the abstract `AIOrb` component's states/motion only.

## Architecture

- **Monorepo**: npm workspaces — `apps/mobile` (Expo/React Native), `packages/appwrite` (schema + provisioning), `functions/*` (Appwrite Functions), `docs/`.
- **Backend**: Appwrite Cloud (`sgp` region), not a custom server. This plan caps Functions at **2 total** — features are consolidated via `body.action` routing inside `generate-insight` and `process-mental-inbox` rather than one function per feature. Don't try to create a third function; add an action to an existing one.
- **AI**: Groq (`openai/gpt-oss-20b` for text, `whisper-large-v3-turbo` for STT) is the primary, working provider. OpenRouter is wired as a fallback but has no purchased credits (untested in practice). Groq's `gpt-oss` reasoning models need `reasoning_effort: 'low'` or they silently return empty content.
- **20+ Appwrite collections** defined in `packages/appwrite/schema.ts` — the single source of truth for the data model. Some collections are provisioned but intentionally unused until a feature needing them is built (check `docs/STATUS.md`/this file's latest state before assuming an unused collection means a bug).

## Dev environment (this machine)

- Android SDK: `C:\Users\chara\AppData\Local\Android\Sdk` (`ANDROID_HOME`/`ANDROID_SDK_ROOT` set persistently). Portable JDK 17 at `C:\Users\chara\tools\jdk-17.0.20.1+1` (`JAVA_HOME` set persistently) — installed manually because `winget install` hangs on a UAC prompt this environment can't answer; if Java tooling goes missing, redownload the zip from Adoptium's API rather than retrying winget.
- The mobile app has a real native dev-client build installed on a physical Android device (Moto G62 5G) reachable via `adb` over WiFi — this is NOT Expo Go. `expo-notifications`, `expo-calendar`, and `react-native-health-connect` only work in this dev-client build.
- `local.properties`'s `sdk.dir` **must** use forward slashes (`C:/Users/...`) — a naive single-backslash Windows path breaks Java's `.properties` parser silently and produces a build failure many steps later with an opaque error.
- Reload the app after a JS-only change: `adb shell am force-stop com.aimentalos.app && adb shell monkey -p com.aimentalos.app -c android.intent.category.LAUNCHER 1`. A native/manifest change needs a real rebuild via `npx expo run:android` (needs `ANDROID_HOME`/`JAVA_HOME`/`PATH` set for that shell — see `docs/STATUS.md` sessions 5-6 for the exact incantation).
- Prefer Maestro (`maestro test flow.yaml`, `tapOn: "<visible text>"`) over hand-computed `adb shell input tap` coordinates — screenshots render at 900x2000 while the device is 1080x2400 (×1.2 scaling, easy to forget mid-sequence). Exception: `tapOn: "Home"` collides with the Android system nav's own "Home" accessibility label — use a unique on-screen string instead, or relaunch the app (it opens on Home by default).
- Appwrite document IDs are capped at 36 characters — a composite key like `${userId}_${longDimensionName}_${windowType}` can exceed this silently; use short codes for composite IDs when the userId alone is already ~20 chars.
- `$createdAt` **can** be set explicitly on `databases.createDocument` when using an API-key (admin) client — useful for seeding backdated historical test data. You cannot spoof `x-appwrite-user-id` on a server-side `functions.createExecution()` call to simulate a specific user (Appwrite rejects it); test a function as a specific user through the real app, or via a real client-side email/password session with `client.setSession(session.secret)`.
- An execution's `responseBody` comes back **empty** from an admin/API-key `functions.getExecution()`/`listExecutions()` call when that execution was created under a real user session — Appwrite redacts it for that scope even though `responseStatusCode`/`content-length` are visible. To confirm what a client action actually wrote, query the target collection directly with the admin client instead of trying to read the execution's response.
- If Metro's normal LAN deep link (`exp://<lan-ip>:8081`) stops reaching the device (bundle requests never arrive, app stuck on splash) after a long idle gap, don't assume the LAN IP changed — check with `adb reverse tcp:8081 tcp:8081` first, then deep-link to `aimentalos://expo-development-client/?url=http%3A%2F%2Flocalhost%3A8081` (localhost, not the LAN IP). This tunnels Metro's port straight over the ADB/USB connection and sidesteps WiFi/firewall issues entirely.
- A top-level side-effecting call in an imported module (e.g. `Notifications.setNotificationHandler(...)` in `notifications.ts`) must be wrapped in try/catch. An unguarded throw at import time aborts the *whole importing module's* evaluation — this once made `app/(tabs)/you.tsx` fail to export its default component (surfacing as expo-router's unrelated-looking "missing the required default export" warning) purely because it imports from `notifications.ts`.
- Tab screens under `app/(tabs)/` fetch their data with a plain `useEffect` on mount, not `useFocusEffect` — switching tabs and back does **not** refetch, so a change made on another screen (e.g. a new `memory_items` doc from `interventions.tsx`) won't show up on the Brain tab until either the screen remounts (app reload) or the user pulls to refresh (`RefreshControl` is wired on every tab). Account for this when verifying a cross-screen effect on-device — a "missing" card immediately after the action that should have produced it is very likely just this, not a broken write; query the collection directly with an admin script to check the write actually happened before treating it as a bug.
- Any screen with a `TextField` needs a `KeyboardAvoidingView` wrapper (`behavior={Platform.OS === 'ios' ? 'padding' : 'height'}` — plain `undefined` on Android does nothing). Without it, a field/button positioned late in a long `ScrollView` (e.g. `community.tsx`'s create-circle form, below the presence card and session carousel) gets squeezed by the opening keyboard down to a few-pixel sliver at the literal bottom edge of the screen — which, being inside Android's gesture-nav exclusion zone, can cause a tap there to trigger the system "go home" gesture instead of the button. Pair the wrapper with a `scrollToEnd()` on the field's `onFocus` (and on whatever toggle first reveals the form) so the field+button actually scroll into the visible, keyboard-adjusted viewport rather than relying on the OS resize alone.
- Confirmed via Maestro's own measured UI bounds (not visual estimation): the "screenshot renders at 900x2000, physical is 1080x2400, ×1.2" rule holds cleanly for X, but Y coordinates near the bottom of the screen do **not** reliably follow the same ×1.2 factor (a tab-bar label estimated at displayed y=1975 was actually at physical y≈2234, not 2370) — treat any hand-computed Y coordinate below roughly the two-thirds mark of the screen as unreliable and prefer Maestro `tapOn: "<text>"` there instead of computing pixels.
- Firing a deep link (`adb shell am start -a android.intent.action.VIEW -d 'aimentalos://...'`) immediately after a fresh `force-stop`+relaunch can race expo-router's linking setup and silently land on the default Home screen instead of the target route, with no error. Wait for both the `ReactNativeJS: Running` logcat line **and** a few more seconds of settle time before firing a post-launch deep link, or verify the landing screen with a screenshot before proceeding.
- `maestro`'s own instrumentation process (`dev.mobile.maestro`) occasionally crashes right after a flow finishes, which can kick the foreground to the Android launcher even though the target app under test is still alive and unaffected — check `adb shell pidof <package>` before concluding the app itself crashed, and relaunch with `monkey -c android.intent.category.LAUNCHER` to bring it back rather than treating it as an app bug.

## Testing

- Function logic uses Node's built-in `node:test` + `assert`, zero external dependencies — run with `node --test` from inside `functions/<name>/src/`. Keep new statistical/deterministic logic in its own pure, dependency-free module (see `patternStats.js`, `baselineStats.js`) so it's testable without any network or Appwrite context.
- When a feature depends on historical data (correlations, baselines, trends), verify it with real seeded sample data against a throwaway test account, not just unit tests in isolation — write a small script in `functions/generate-insight/scripts/` (delete it after use), seed realistic values with a deliberately engineered signal, and confirm the feature finds the exact thing that was planted.
- Deploy a function after any change to it: `cd functions/generate-insight && node scripts/deploy.mjs`, then poll `scripts/check-status.mjs` or `functions.listDeployments()` until `status: 'ready'` before testing — deployments build asynchronously.
- Check real errors from a failing execution via `functions/generate-insight/scripts/check-executions.mjs` — client-facing error messages are deliberately sanitized (`respond.js#failSafely()`), so the real stack trace only shows up in Appwrite's execution logs, not the API response.
