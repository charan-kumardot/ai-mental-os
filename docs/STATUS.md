### Two real bugs found and fixed during this pass (both genuine regressions, not new-feature issues)
1. **Appwrite Realtime's `window.localStorage.getItem` crash** — the Appwrite web SDK's Realtime client does an unguarded `window.localStorage.getItem('cookieFallback')` the moment a socket connects without a `config.session` set (our mobile auth flow never sets one — that's a browser-cookie concept). It's internally try/caught, so nothing actually broke, but the resulting `console.error` tripped React Native's dev LogBox into a red error overlay on every Realtime subscribe. Fixed with a minimal `window.localStorage` stub in `src/lib/appwrite.ts`, loaded before any Appwrite code runs.
2. **`expo-notifications` crash-at-import regression** — mid-session, `expo-notifications`'s own module started throwing synchronously the moment it's imported (not just when a function on it is called), apparently deciding the runtime looked like Expo Go. The existing guard in `src/lib/notifications.ts` only wrapped the later `setNotificationHandler` call in try/catch — a `try` block can't catch a throw from a hoisted `import` statement. This cascaded into `app/(tabs)/you.tsx` (which imports `notifications.ts`) failing to export its default component, taking down the whole app (an Expo dev-client "Something went wrong" screen, not a silent failure). Fixed by converting the static `import` to a guarded `require()`, with every exported function now no-op'ing when the module fails to load. This is the same failure class already documented in `CLAUDE.md` (side-effecting top-level imports must be crash-proof) — worth strengthening that note to explicitly cover "even the bare `import` statement, not just calls on the resulting module."
3. **Stale Metro bundle, same root cause as prior sessions' documented gotcha** — repeated JS edits stopped taking visible effect mid-session; killing the Metro process (`netstat`-located, `taskkill /F /T`) and restarting with `--clear` resolved it. Confirms this class of issue isn't rare enough to treat as a one-off; `CLAUDE.md`'s existing note on this should be trusted immediately rather than re-diagnosed from scratch each time it recurs.

### Personal Baseline Engine + Personal State Engine + Baseline Drift (spec §13-16) ✅
- `functions/generate-insight/src/baselineStats.js` — pure, unit-tested math (13 tests). Computes short/7d, medium/30d, long/90d mean+stdDev per dimension (mood, sleep, steps, meeting count), each window only populated once it has its own honest minimum sample count. `detectDrift()` flags when the medium baseline has moved >0.75 stdDev from the long one — "your normal has changed," not just "today is unusual." `computeStateEstimate()` compares today's real value against the short baseline via z-score into low/moderate/high — **Focus and Stress are always left `null`**, never defaulted to "moderate," because no real signal exists for them anywhere in this app. Mental load is a genuine composite of two real signals (meeting count + unresolved Mental Inbox count), not invented.
- `functions/generate-insight/src/stateEngine.js` (new `compute_state` action) + `src/lib/stateEngine.ts` — orchestrates the above against real Appwrite data, upserts to the two previously-unused collections.

- **Real bug found and fixed during this verification** (not a shortcut — a genuine Appwrite constraint): composite baseline document IDs (`${userId}_${dimension}_${windowType}`) silently exceeded Appwrite's 36-character document-ID limit for the longer dimension names. Shortening the ID scheme created a second bug — old documents from an earlier partial deploy (created under the full-word ID scheme, for the dimensions whose names happened to fit) became orphaned from the new short-code IDs while still holding the same unique-index values, so every update said "not found" and every create said "unique constraint violation." Fixed properly by switching the upsert to look up the existing document by its real field values (`Query.equal` on userId+dimension+windowType) rather than by a guessed ID — self-healing regardless of ID-scheme history, not just a one-time patch.

### Contradiction Engine + prediction calibration (spec §20-21) ✅
- `functions/generate-insight/src/detectPatterns.js` no longer treats a cached pattern as permanently true. On a forced refresh, every already-tracked pattern's specific dimension pair is re-correlated against the latest data (`correlatePair()`, new in `patternStats.js`, 4 new tests): if it still holds, confidence is recalculated from the fresh r/n and the contradiction streak resets; if it doesn't, the streak increments, confidence genuinely decays (not reset to 0), and after a second consecutive contradiction the pattern is retired rather than kept around indefinitely as a stale claim. This is genuine calibration — a pattern's confidence now responds to new evidence instead of being frozen at creation — and it's what finally gives the schema's `contradictingCount`/`status` fields real behavior instead of `contradictingCount: 0` as a permanent dead literal.
- Extracted the day-aggregation logic both engines depend on into a shared `dayMap.js` module rather than duplicating it (it previously lived only inside `detectPatterns.js`).
